1. Functional Description  
For each provided rectangular grid, computes the minimum number of “terrain changes” required to reach any boundary cell from a designated start cell, where moving to an orthogonally adjacent cell costs 0 if the destination cell has the same terrain as the current cell and costs 1 if it differs. The reported value is half of that minimum cost using integer division.

2. Inputs  
- Repeated test cases.  
- Each test case provides:  
  - Two integers: grid width and grid height.  
  - A grid of height rows and width columns of single-character cell values, containing exactly one designated start marker.  
- Termination occurs when both width and height are zero.

3. Outputs  
- For each test case, outputs a single integer: the minimum over all boundary cells of (minimum terrain-change cost from the start to that boundary cell) divided by 2 using integer division.

4. Preconditions  
- Width and height are within the supported fixed maximum (at most 101 each).  
- The grid contains exactly one start marker.  
- All grid characters are valid cell values; the start marker is treated as a normal cell of a specific terrain for movement-cost purposes (see assumptions in Postconditions).  
- The input provides enough characters to fill the grid for each test case.

5. Postconditions  
- For every cell in the grid, a minimum terrain-change cost from the start to that cell is well-defined and finite (the grid is fully connected under orthogonal moves).  
- The produced output equals:  
  - Let cost(p) be the minimum number of times a move crosses between different cell characters along any orthogonal path from the start to boundary cell p, where the start cell’s marker is treated as a normal cell with the same terrain as the “empty” terrain character.  
  - Output is min over all boundary cells p of ⌊cost(p) / 2⌋.

6. Invariants  
- Movement is only between orthogonally adjacent in-bounds cells.  
- The computed cost for any cell never increases once a lower cost has been established.  
- All costs are non-negative integers.

7. Error Handling / Exceptional Behavior  
- No explicit error handling is performed.  
- If preconditions are violated (e.g., missing start marker, dimensions exceeding limits, malformed input), behavior is undefined (may produce incorrect output or access invalid memory).

8. State Transitions (if applicable)  
- The program processes independent test cases until the terminating dimensions are read.  
- For each test case, internal state is reinitialized and does not carry over to the next test case.

9. Non-functional Constraints (if inferable)  
- Supports grids up to 101×101 due to fixed-size storage.  
- Uses fixed-size work queues sized for up to 200,000 entries; exceeding this through unexpected behavior would be unsafe.
