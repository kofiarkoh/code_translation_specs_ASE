# Code Specification

## 1. Functional Description
- **High-level description of the purpose**: The code implements a graph-based algorithm to determine whether pairs of nodes in a directed graph are "different" or "same" based on their connectivity and reachability.
- **What problem it solves**: It identifies whether there exists a path between two nodes in a directed graph, considering the structure of strongly connected components (SCCs).
- **Core behavior**: The program reads a directed graph from input, computes its SCCs, and then checks for each edge if the nodes it connects are in the same SCC or if they can reach each other through other nodes.

## 2. Inputs
- **Parameters**:
  - `n`: Number of nodes in the graph.
  - `m`: Number of edges in the graph.
  - Pairs of integers representing directed edges between nodes.
- **Data types**:
  - `int` for node and edge counts, and indices.
  - `char` for marking visited nodes and differences.
- **Valid ranges or constraints**:
  - `n` must be greater than 0 and less than or equal to `N` (1000).
  - `m` must be greater than or equal to 0 and less than or equal to `M` (200000).
  - Node indices in edges must be within the range [0, n-1].
- **Assumptions about inputs**: The input graph is assumed to be directed and may contain cycles.

## 3. Outputs
- **Return values**: The program does not return a value but prints results to standard output.
- **Side effects**: Outputs the relationship status ("diff" or "same") for each edge in the graph.
- **Output format/schema**: Each line corresponds to an edge, with "diff" indicating the nodes are different and "same" indicating they are the same.

## 4. Preconditions
- **Conditions that must hold before execution**: The input must be correctly formatted, with valid integers for `n` and `m`, followed by `m` pairs of integers representing edges.
- **Explicit logical constraints**: The graph must not exceed the defined limits for nodes and edges.

## 5. Postconditions
- **Conditions guaranteed after execution**: The program will output a line for each edge indicating whether the nodes are "diff" or "same".
- **State changes**: The internal state of various arrays (e.g., `cc`, `visited`, `diff`) will be modified to reflect the results of the computations.
- **Return guarantees**: The program will always produce output for each edge based on the computed relationships.

## 6. Invariants
- **Conditions that must always remain true**: The arrays used for tracking nodes and edges (e.g., `ae`, `af`, `cc`, `visited`) must maintain valid indices and states throughout the execution.
- **Class-level invariants**: Not applicable as the code does not define any classes.

## 7. Error Handling / Exceptional Behavior
- **What happens on invalid input?**: The behavior is undefined; the program may produce incorrect results or crash.
- **Exceptions thrown?**: The code does not explicitly handle exceptions; it relies on valid input.
- **Edge-case behavior**: If `n` or `m` is zero, the program will not process any edges and will output nothing.

## 8. State Transitions (if applicable)
- **Valid object states**: The program maintains states for nodes (visited, component membership) and edges (difference status).
- **State changes caused by execution**: The execution modifies the `visited` and `cc` arrays to reflect the traversal and component identification.

## 9. Non-functional Constraints (if inferable)
- **Time complexity**: The algorithm primarily involves depth-first searches (DFS), leading to a time complexity of O(n + m).
- **Space complexity**: The space complexity is O(n + m) due to the storage of adjacency lists and other arrays.
- **Performance assumptions**: The algorithm is expected to perform efficiently within the constraints of the problem, handling the maximum input sizes in a reasonable time frame.
