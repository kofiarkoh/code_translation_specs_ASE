# Code Specification

## 1. Functional Description
- **High-level description of the purpose**: The code implements a directed graph using an adjacency list representation and provides functionality to detect cycles within the graph.
- **What problem it solves**: It allows users to create a directed graph, add edges, and determine if the graph contains any cycles, which is crucial for various applications in computer science, such as scheduling and dependency resolution.
- **Core behavior**: The program initializes a graph, accepts user input to populate it with edges, and checks for cycles, returning a boolean result.

## 2. Inputs
- **Parameters**:
  - `num_vertex`: Number of vertices in the graph (input during graph creation).
  - `source`: The source vertex for adding an edge.
  - `edge`: A structure containing the target vertex and cost of the edge.
- **Data types**:
  - `int` for vertex indices and edge costs.
  - `struct edge` for edge representation.
  - `struct adjcency_list` for the graph structure.
- **Valid ranges or constraints**:
  - `num_vertex` must be a positive integer.
  - `source` must be a valid index within the range of vertices (0 to `num_vertex - 1`).
- **Assumptions about inputs**: It is assumed that the user provides valid input as per the expected format.

## 3. Outputs
- **Return values**:
  - The function `is_cyclic` returns `1` if a cycle is detected and `0` otherwise.
- **Side effects**: The program modifies the internal state of the graph by adding edges.
- **Output format/schema**: The output is a single integer printed to the console, indicating the presence of a cycle.

## 4. Preconditions
- **Conditions that must hold before execution**:
  - The graph must be initialized using `make_adjcency_list` before adding edges or checking for cycles.
  - The number of edges must not exceed the maximum possible edges for the given number of vertices.
- **Explicit logical constraints**: The input for vertices and edges must be non-negative integers.

## 5. Postconditions
- **Conditions guaranteed after execution**:
  - The graph structure is updated with the newly added edges.
  - The cycle detection function returns a definitive result based on the current state of the graph.
- **State changes**: The adjacency list is modified to include new edges.
- **Return guarantees**: The return value from `is_cyclic` accurately reflects the presence of cycles in the graph.

## 6. Invariants
- **Conditions that must always remain true**:
  - The adjacency list must maintain a valid structure, with each vertex having a linked list of edges.
  - The `num_edge` field for each vertex must accurately reflect the number of edges originating from that vertex.

## 7. Error Handling / Exceptional Behavior
- **What happens on invalid input?**: The program does not handle invalid input gracefully; it may lead to undefined behavior or crashes.
- **Exceptions thrown?**: No explicit exceptions are thrown; memory allocation failures may lead to crashes.
- **Edge-case behavior**: If `num_vertex` is zero or negative, the behavior is undefined.

## 8. State Transitions (if applicable)
- **Valid object states**: The graph can be in an uninitialized state, an initialized state with no edges, or a populated state with edges.
- **State changes caused by execution**: Adding edges modifies the state of the graph, increasing the number of edges and potentially altering the cycle status.

## 9. Non-functional Constraints (if inferable)
- **Time complexity**: The cycle detection function operates in O(V + E) time, where V is the number of vertices and E is the number of edges.
- **Space complexity**: The space complexity is O(V + E) due to the storage of the adjacency list and the in-degree array.
- **Performance assumptions**: The performance is contingent on the number of vertices and edges, with larger graphs leading to longer execution times.
