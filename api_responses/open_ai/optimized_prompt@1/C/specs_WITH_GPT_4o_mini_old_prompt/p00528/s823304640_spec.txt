# Code Specification

## 1. Functional Description
- **High-level description of the purpose**: The code implements a solution to find the shortest path in a grid-like structure, specifically for navigating through a modern mansion represented as a graph.
- **What problem it solves**: It determines the minimum distance required to travel from a starting point to a goal point in a grid, considering obstacles and connections between points.
- **Core behavior**: The program reads input for the dimensions of the mansion and the positions of obstacles, constructs a graph representation, and uses Dijkstra's algorithm to compute the shortest path.

## 2. Inputs
- **Parameters**:
  - `m`: Number of rows in the mansion (grid).
  - `n`: Number of columns in the mansion (grid).
  - `k`: Number of obstacles.
  - Coordinates of obstacles (pairs of integers).
- **Data types**:
  - `int` for dimensions and coordinates.
  - `long long` for distance calculations.
- **Valid ranges or constraints**:
  - `m`, `n` must be positive integers.
  - `k` must be non-negative.
  - Coordinates must be within the bounds of the grid defined by `m` and `n`.
- **Assumptions about inputs**: The input is assumed to be well-formed and within the specified constraints.

## 3. Outputs
- **Return values**: The program outputs a single `long long` integer representing the minimum distance from the start to the goal. If no path exists, it returns `-1`.
- **Side effects**: The program prints the result to standard output.
- **Output format/schema**: A single line containing the minimum distance or `-1`.

## 4. Preconditions
- **Conditions that must hold before execution**:
  - The input must be provided in the expected format.
  - The grid dimensions (`m`, `n`) and the number of obstacles (`k`) must be valid.
- **Explicit logical constraints**: The starting point must be defined within the grid, and the goal point must also be defined.

## 5. Postconditions
- **Conditions guaranteed after execution**:
  - The program will have computed the shortest path distance or determined that no path exists.
- **State changes**: The internal state of the queue and graph representation will be modified during execution.
- **Return guarantees**: The output will either be a valid distance or `-1`.

## 6. Invariants
- **Conditions that must always remain true**:
  - The queue used for Dijkstra's algorithm is maintained as a min-heap.
  - The graph representation remains consistent with the input obstacles and connections.

## 7. Error Handling / Exceptional Behavior
- **What happens on invalid input?**: The behavior on invalid input is not explicitly defined; the program may exhibit undefined behavior or crash.
- **Exceptions thrown?**: No exceptions are explicitly handled in the code.
- **Edge-case behavior**: If the start or goal points are not defined, the program may not function as intended.

## 8. State Transitions (if applicable)
- **Valid object states**: The program maintains a state representing the current position in the graph and the distances calculated.
- **State changes caused by execution**: The state of the queue and the visited nodes changes as the algorithm progresses.

## 9. Non-functional Constraints (if inferable)
- **Time complexity**: The time complexity is O((V + E) log V), where V is the number of vertices and E is the number of edges, due to the use of Dijkstra's algorithm with a priority queue.
- **Space complexity**: The space complexity is O(V) for storing the graph and the queue.
- **Performance assumptions**: The program is expected to perform efficiently for reasonably sized inputs, but performance may degrade with very large grids or numerous obstacles.
