# Code Specification

## 1. Functional Description
- **High-level description of the purpose**: The code implements a simple grid-based game where a player can move, push, pull, climb, and drop blocks on a map, with the goal of reaching a designated goal position.
- **What problem it solves**: It provides a framework for simulating movement and interactions within a 2D grid, allowing for basic game mechanics and win/lose conditions.
- **Core behavior**: The player can execute commands to manipulate their position and the blocks on the map, while the game checks for win/lose conditions after each command.

## 2. Inputs
- **Parameters**:
  - `height`: The number of rows in the grid.
  - `width`: The number of columns in the grid.
  - `command_num`: The number of commands to be executed.
  - `command`: The type of action to perform (e.g., MOVETO, PUSH, PULL, CLIMB, GETDOWN).
  - `command2`: Additional parameter for commands (e.g., direction or position).
- **Data types**: 
  - `int` for dimensions and command counts.
  - `char` arrays for the map and commands.
- **Valid ranges or constraints**: 
  - `height` and `width` must be positive integers.
  - `command_num` must be non-negative.
  - `command` must be one of the predefined action strings.
- **Assumptions about inputs**: The input map is well-formed and contains valid characters representing the player, goal, blocks, and empty spaces.

## 3. Outputs
- **Return values**: The program does not return values but outputs game status messages to the console.
- **Side effects**: The state of the game grid is modified based on player actions, and the game status is printed to the console.
- **Output format/schema**: Game over messages are printed in a specific format indicating the outcome (e.g., "Game Over : Cleared").

## 4. Preconditions
- **Conditions that must hold before execution**: 
  - The grid dimensions must be set and valid.
  - The map must be initialized with the player ('S') and goal ('G') positions.
- **Explicit logical constraints**: The game should not start with an invalid map configuration.

## 5. Postconditions
- **Conditions guaranteed after execution**: 
  - The game state reflects the results of the executed commands.
  - The game over status is determined based on the player's final position and interactions.
- **State changes**: The player's position and the state of the map are updated based on the commands executed.
- **Return guarantees**: The program will output a game over message based on the final game state.

## 6. Invariants
- **Conditions that must always remain true**: 
  - The player's position must always be within the bounds of the grid.
  - The map must always contain valid characters representing the game elements.
- **Class-level invariants**: Not applicable as the code does not utilize classes.

## 7. Error Handling / Exceptional Behavior
- **What happens on invalid input?**: The program may terminate or behave unpredictably if the input does not conform to expected formats.
- **Exceptions thrown?**: The code does not explicitly handle exceptions; it relies on valid input.
- **Edge-case behavior**: If the player attempts to move outside the grid or into an invalid position, the command will be ignored.

## 8. State Transitions
- **Valid object states**: The game can be in various states based on the player's position and the state of the blocks (e.g., moving, pushing, pulling).
- **State changes caused by execution**: Each command modifies the player's position and the map, potentially leading to a game over state.

## 9. Non-functional Constraints
- **Time complexity**: The complexity of command execution varies; moving and pushing blocks may involve iterating through the grid, leading to O(n*m) in the worst case, where n is height and m is width.
- **Space complexity**: The space complexity is O(n*m) due to the storage of the map.
- **Performance assumptions**: The game is expected to perform efficiently for reasonably sized grids (up to 51x51 as defined).
