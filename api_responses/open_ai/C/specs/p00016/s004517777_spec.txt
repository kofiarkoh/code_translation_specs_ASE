1. Functional Description
   - High-level: Command-line program that reads a sequence of numeric movement commands and computes a final 2D position, then prints the integer parts of the final coordinates.
   - Problem solved: Integrates successive forward movements and rotations to produce a final position (a simple turtle-like motion accumulator).
   - Core behavior (intended): For each input pair (mov, dir) it moves the current position by mov units in the current heading (degrees), then rotates the heading by dir degrees. Stops when the pair 0,0 is read, then prints the final x and y coordinates as integers (truncated).

   Note: The compiled code as written uses x, y, d without initialization, which yields undefined behavior. The remainder of this specification describes both the actual/unsafe consequence (uninitialized variables) and the intended/assumed behavior if x, y, d are 0 at start (stated explicitly where assumed).

2. Inputs
   - Parameters: None (reads from standard input).
   - Input items: A sequence of pairs of floating-point numbers formatted as "<mov>,<dir>" (scanned by scanf with format "%lf,%lf").
   - Data types: mov and dir are double-precision floating-point values.
   - Valid ranges / constraints:
     - mov and dir should be representable as double; NaN/Inf are possible but not specially handled.
     - Each pair must include a literal comma separating the two numbers (scanf "%lf,%lf" requires a comma).
     - The sequence must contain a terminating sentinel pair 0,0 to cause normal termination; otherwise termination behavior is not guaranteed.
   - Assumptions about inputs (for intended behavior):
     - Inputs are well-formed numeric pairs separated by commas and whitespace/newlines as appropriate.
     - A terminating pair 0,0 is provided eventually.

3. Outputs
   - Return value: Program returns process exit code 0 upon normal completion.
   - Standard output: Two lines containing the integer conversions of final x and y:
     - First printed line: (int)x followed by newline.
     - Second printed line: (int)y followed by newline.
     - Conversion behavior: C cast (int)x truncates toward zero (no rounding).
   - Side effects:
     - Reads from stdin until the loop termination condition is met (mov==0 && dir==0).
     - Writes formatted text to stdout.
   - Output schema: Two 32-bit integer text lines (format "%d\n%d\n") reflecting truncated final coordinates.

4. Preconditions
   - Required for well-defined, intended behavior:
     - Initial numeric state (x, y, d) must be well-defined before the first iteration. The code does not initialize them; therefore, to avoid undefined behavior the execution environment must ensure they have defined values (in practice, they should be treated as if initialized to known values, typically 0.0).
     - Input stream must contain correctly formatted pairs "<mov>,<dir>".
     - A sentinel pair 0,0 must appear to terminate the loop normally.
   - Logical constraints:
     - mov and dir are finite doubles (NaN/Inf are not handled specially).
     - scanf must successfully parse pairs; otherwise mov and dir may be left unchanged.

5. Postconditions
   - If execution completes normally (i.e., loop exits because a read pair equals 0,0 and no undefined behavior occurred):
     - Final x and y equal the cumulative result of sequential updates:
       x_final = x_initial + sum_i mov_i * sin(d_i * π/180)
       y_final = y_initial + sum_i mov_i * cos(d_i * π/180)
       where d_{i+1} = d_i + dir_i and d_0 is the initial heading.
     - The program has printed (int)x_final and (int)y_final on separate lines.
     - Process exits with code 0.
   - If variables are uninitialized or input malformed, no postconditions are guaranteed (see Error Handling).

6. Invariants
   - Mathematical invariant across iterations (assuming defined numeric state):
     - After k processed commands, the heading d equals initial_heading + sum_{i=1..k} dir_i.
     - Position updates preserve the form x += mov * sin(d_in_degrees) and y += mov * cos(d_in_degrees) at each step.
   - Program-level invariants:
     - The program reads pairs in the same order they appear in stdin.
     - The loop condition is based solely on the most recently read mov and dir values being both zero.

7. Error Handling / Exceptional Behavior
   - Uninitialized variables: The code declares x, y, d but does not initialize them. Using them before initialization is undefined behavior in C; therefore program behavior is undefined unless those variables happen to contain defined values (not guaranteed).
   - Malformed input:
     - If scanf fails to parse a pair (e.g., missing comma, non-numeric tokens, EOF), scanf return value is ignored; mov and dir retain their previous values (or remain uninitialized on first iteration), which can cause incorrect behavior or infinite loop.
     - If EOF occurs before a terminating 0,0 pair, and mov/dir do not become 0, the loop may not terminate; behavior is not guaranteed.
   - No explicit exceptions or error messages are produced by the program.
   - Edge cases:
     - mov = 0 and dir != 0: the loop will process the rotation (d += dir) only if the loop body executes; however because the loop body is guarded by the condition mov!=0 || dir!=0 which is evaluated after reading, mov=0,dir!=0 causes body to run (since condition true) and then the next iteration proceeds.
     - NaN/Inf values propagate through math functions sin/cos producing implementation-defined results; no checks are performed.

8. State Transitions
   - Valid conceptual object states (state is the triple (x,y,d)):
     - Any triple of finite doubles (assuming initialization).
   - Transition on processing one input pair (mov,dir):
     - new_x = old_x + mov * sin(old_d * π/180)
     - new_y = old_y + mov * cos(old_d * π/180)
     - new_d = old_d + dir
   - Terminal state:
     - Reached when the last-read pair equals (0.0, 0.0) — when that pair is read the loop body is not executed for that pair and the program proceeds to print and exit.
   - If initial state is undefined, transitions are undefined.

9. Non-functional Constraints (inferable)
   - Time complexity: O(n) where n is the number of input pairs processed up to the terminating (0,0) pair (each pair causes constant work: two trig calls, three arithmetic ops).
   - Space complexity: O(1) extra space (constant memory).
   - Performance assumptions:
     - Dependent on library implementations of scanf, sin, cos.
     - Floating-point precision limited by double.
   - Portability notes:
     - Behavior depends on C implementation with respect to undefined behavior from uninitialized variables; results are not portable unless variables are initialized.

Summary of ambiguous/unsafe aspects
   - The code, as written, exhibits undefined behavior because x, y, and d are uninitialized. All guarantees above require the explicit assumption that x, y, and d are initialized (commonly to 0.0) before the first iteration. If that assumption is not met, no stable behavioral guarantees can be made.
