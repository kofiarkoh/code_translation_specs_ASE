1. Functional Description
   - High-level description:
     The program determines, for each test case, whether a single agent starting at a given grid cell can remain "alive" through a sequence of n steps, where at step u the agent must occupy a cell within the 3x3 neighborhood centered at a given scout coordinate sc[u], and each step must be reachable from a previous allowed cell using a fixed finite set of move offsets.
   - What problem it solves:
     It solves a reachability/survivability check on a fixed-size 2D grid: given a start cell and a sequence of constrained target neighborhoods, it decides if there exists a sequence of cells (one per step) satisfying both neighborhood membership and per-step move reachability constraints.
   - Core behavior:
     For each test case (start coordinate and list of scout coordinates), it iteratively computes the set of possible agent cells after each scout such that:
       - the cell lies within the 3x3 neighborhood of the current scout, and
       - it is reachable from any previously possible cell using one of 12 predefined move offsets.
     If at any step the set becomes empty, the case is declared impossible ("NA"); if after processing all scouts at least one possible cell remains, the case is declared possible ("OK").

2. Inputs
   - Parameters:
     Input is read from standard input as multiple test cases. Each test case consists of:
       1. Two integers sx, sy — starting coordinates.
       2. One integer n — number of scout positions.
       3. n pairs of integers scx[i], scy[i] — scout coordinates for i = 0..n-1.
     Test cases repeat until a start pair of "0 0" is read (that pair terminates processing and is not processed as a case).
   - Data types:
     All coordinates and n are integers.
   - Valid ranges or constraints (assumptions required for correct behavior):
     - Grid coordinates are intended to be within [0, 9] (inclusive) — i.e., a 10x10 grid indexed 0..9.
     - 0 <= n <= 10 (maximum number of scouts).
     - Number of scout coordinates per case equals n.
     - The program expects at most 10 scouts and grid coordinates within 0..9; inputs violating these bounds lead to undefined behavior (see Error Handling).
   - Assumptions about inputs:
     - The terminating start coordinate (0,0) is used solely to end input and is not processed.
     - All numeric values are well-formed integers in the input stream.
     - If any coordinate used in a test case is outside the grid [0,9], behavior is not defined by the specification.

3. Outputs
   - Return values:
     - The program writes one line per processed test case to standard output:
       - "OK" if survival through all n scouts is possible.
       - "NA" if survival is impossible (the set of possible positions becomes empty at some step).
   - Side effects:
     - Reads from standard input until the sentinel start coordinate 0 0 is encountered.
     - Writes the textual result lines to standard output.
   - Output format/schema:
     - Each processed test case produces a single line exactly containing either OK or NA followed by a newline.

4. Preconditions
   - Conditions that must hold before execution for defined behavior:
     - The input stream contains sequences of integers formatted as described (sx sy, then n, then n pairs).
     - For each test case processed (i.e., before invoking the survivability check):
       - n is within the acceptable bound (assumed 0 <= n <= 10).
       - All coordinates (sx, sy, scx[i], scy[i]) intended for processing are within [0,9].
     - The sentinel (0,0) appears eventually to terminate processing; otherwise the program will attempt to read indefinitely.
   - Explicit logical constraints:
     - The number of scout coordinate pairs following an n value must be exactly n.

5. Postconditions
   - Conditions guaranteed after execution of a test case:
     - The program outputs a single status string ("OK" or "NA") for that test case to stdout:
       - "OK" implies: there exists at least one sequence p0..pn of grid cells such that p0 = (sx,sy), and for every step u in 0..n-1:
         - pu+1 is within the 3x3 neighborhood centered at sc[u], and
         - pu+1 is equal to pu plus one of the allowed move offsets, and
         - all coordinates in the sequence are within the grid bounds [0,9].
       - "NA" implies: no such sequence exists (the set of candidate positions becomes empty at some step).
   - State changes:
     - Program internal ephemeral state (per-case candidate sets) is updated across steps; no persistent external state is modified by a test case aside from printed output.
   - Return guarantees:
     - For each valid test case, exactly one of "OK" or "NA" is printed.

6. Invariants
   - Conditions that remain true throughout processing of a test case:
     - Candidate positions always lie within the grid bounds [0,9].
     - The set of candidate positions considered at each step is a subset of the 3x3 neighborhood of the current scout coordinate.
     - The number of candidate positions per step is at most 9 (the size of a 3x3 neighborhood).
   - Program-level invariants:
     - Each processed test case produces exactly one output line.
     - The termination condition (start coordinate equals 0 0) will stop reading further cases.

7. Error Handling / Exceptional Behavior
   - Invalid input:
     - If input does not follow the expected integer sequence (missing values, non-integers), the behavior is undefined (program may block or terminate with I/O error).
     - If n is negative or greater than the assumed maximum (10), or if more than the expected number of coordinate pairs are present, behavior is undefined.
     - If coordinates fall outside the intended grid [0,9], behavior is undefined.
   - Exceptions thrown:
     - The program does not raise language-level exceptions; on malformed input it will typically cause undefined behavior or I/O failure.
   - Edge-case behavior:
     - n = 0: Survival is trivially successful if the start coordinate is not the sentinel (0,0); the program will output "OK" (since no scout constraints to violate).
     - If at any step no candidate positions remain, the program immediately outputs "NA" for that test case and proceeds to the next case.
     - The special sentinel start coordinate (0,0) terminates processing without producing an output line.

8. State Transitions (if applicable)
   - Valid object/process states per test case:
     - Initial state: candidate set = {start coordinate}.
     - After processing each scout u: candidate set = {cells in 3x3 neighborhood of sc[u] that are reachable from any cell in previous candidate set by one move offset and are inside grid bounds}.
     - Terminal success state: after processing all scouts, candidate set is non-empty -> output "OK".
     - Terminal failure state: candidate set becomes empty at some step -> output "NA" immediately.
   - State changes caused by execution:
     - Each step replaces the candidate set with the intersection of (neighborhood of the current scout) and (the union of move-offset images of the previous candidate set), restricted to grid bounds.

9. Non-functional Constraints (if inferable)
   - Time complexity:
     - For a single test case with n scouts, the algorithm examines at most a constant number of candidate positions (<=9) and a constant number of moves (12) per step; therefore time is O(n) with a small constant factor.
   - Space complexity:
     - Uses fixed-size buffers and arrays independent of input size (bounded by constants MAX_M=10, MAX_N=10, MAX_G=9), so space is O(1).
   - Performance assumptions:
     - All operations execute with constant-time arithmetic and array accesses; overall performance scales linearly with the number of scouts n per test case.

Notes on ambiguity
   - The specification assumes grid coordinates and n are constrained to the intended bounds (grid 0..9, n <= 10). If inputs violate those bounds, program behavior is not specified here.
