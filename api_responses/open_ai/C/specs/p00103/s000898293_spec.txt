1. Functional Description
   - High-level description:
     - A command-line program that simulates scoring for a sequence of baseball half-innings (or game segments). For each segment it reads a sequence of events and computes the total runs scored until three outs occur.
   - Problem it solves:
     - Given an integer count of segments and, for each segment, a stream of event tokens, compute and output the number of runs scored in that segment according to simple base-running rules.
   - Core behavior:
     - For each segment, start with empty bases and zero outs. Process event tokens one-by-one until three outs have occurred. Valid events are "HIT", "HOMERUN", and "OUT". After three outs, output the total runs scored for that segment, then proceed to the next segment until the initial count is exhausted.

2. Inputs
   - Parameters / source:
     - Read from standard input (stdin).
   - Expected tokens and types:
     - First token: an integer n (number of segments to process).
     - Following tokens: a sequence of whitespace-delimited strings (char sequences) representing events. Valid event strings: "HIT", "HOMERUN", "OUT".
   - Valid ranges / constraints:
     - n is expected to be a non-negative integer. If n == 0, the program produces no outputs and exits normally.
     - Event tokens must exactly match one of the three valid uppercase strings.
     - Event strings should fit within 7 characters + null terminator (the code allocates space for up to 7-character tokens).
   - Assumptions about input:
     - There are sufficient event tokens provided to reach three outs for each of the n segments.
     - Events are provided in order and formatted exactly as uppercase tokens "HIT", "HOMERUN", or "OUT".

3. Outputs
   - Return values:
     - Program returns exit code 0 on normal completion.
   - Standard output:
     - For each processed segment, a single line containing the integer number of runs scored during that segment, followed by a newline. One line per segment, in the same order segments were processed.
   - Side effects:
     - Reads from stdin and writes to stdout only.

4. Preconditions
   - The first input token is an integer n (number of segments). n should be a non-negative integer if normal termination is expected.
   - For each of the n segments, the input provides an adequate sequence of event tokens that includes at least three "OUT" events (so the segment can terminate).
   - Event tokens must be exact uppercase strings "HIT", "HOMERUN", or "OUT".
   - Event tokens should not exceed 7 characters in length.

5. Postconditions
   - For each segment processed:
     - The program prints exactly one integer line equal to the total runs scored in that segment.
     - The printed value is the count of batters and base runners who crossed home plate during processing up to the third out.
   - After processing all n segments, the program exits with status 0.
   - No persistent state is retained between segments (bases and out count are reset at the start of each segment).

6. Invariants
   - At the boundaries between processing of events (i.e., after each event is fully applied), the occupancy state for each base is logically either occupied or empty (i.e., treated as boolean occupied/unoccupied for the purpose of scoring and advancement).
   - The program emits exactly one output line for each processed segment.
   - Event processing for a segment continues until the out count for that segment reaches 3.

7. Error Handling / Exceptional Behavior
   - Invalid or unexpected event strings:
     - If an event token is not exactly "HIT", "HOMERUN", or "OUT", the program does not alter outs, bases, or score for that token and continues to read the next token; if such tokens continue indefinitely, the segment will not terminate (i.e., processing may hang waiting for sufficient "OUT" tokens).
   - Insufficient input (EOF before reaching three outs for a segment or before reading n):
     - Not inferable deterministically from code; practically, the program will block waiting for input if running interactively, or may repeatedly process previous or undefined data if scanf fails to provide new data — behavior is undefined from the caller's perspective.
   - Oversized event tokens (>7 characters):
     - Not handled safely by the program; buffer overflow risk exists (undefined behavior).
   - Negative n:
     - The code treats any non-zero integer as "process until n reaches 0 by decrementing," so negative n leads to indefinite processing until input exhaustion; this is outside intended use.
   - No explicit error messages are produced.

8. State Transitions (per segment)
   - Valid object/state variables:
     - outs: integer counter starting at 0, valid range [0, 3] during processing, segment ends when outs == 3.
     - bases: three occupancy indicators for first, second, third base. Conceptually boolean (occupied/unoccupied).
     - score: non-negative integer, increments when a runner reaches home plate due to an advance or homerun.
   - Effects of events:
     - "HIT": batter occupies first base; existing runners (if any) advance one base each; any runner who advances beyond third base increments score by 1 and is removed from bases.
     - "HOMERUN": all runners on bases each score 1 (removed from bases), and the batter also scores 1.
     - "OUT": outs increments by 1; no change to bases or score.
   - Transition guarantees:
     - After any event, bases reflect the new occupancy derived from that event and any resulting scoring; outs is incremented only by "OUT".
     - Segment ends immediately after the event that causes outs to reach 3, and the segment's score is output.

9. Non-functional Constraints
   - Time complexity:
     - Linear in the number of processed event tokens: O(E), where E is total events consumed from input. Each event is processed in constant time (bounded loop of size 3).
   - Space complexity:
     - O(1) additional space: a fixed small amount of memory (constant-sized base array and counters).
   - Performance assumptions:
     - Assumes timely delivery of input tokens; no internal buffering beyond stdin reading. Performance per event is constant and small.

Notes / Ambiguities
   - The program expects exact uppercase event tokens; lowercase variants or alternate spellings are not considered valid.
   - Behavior on malformed input, EOF before sufficient events, oversized tokens, or negative n is not robustly handled; these cases are either undefined or lead to non-termination. These limitations are not mitigated by the program.
